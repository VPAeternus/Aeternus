# Scout Compiler and Scenario Retriever Contracts Design

**Date:** 2026-03-15

## Goal

Define a non-interfering `v1` contract for:

- `Scout Compiler`
- `Event Card`
- `Coverage Precheck`
- `Scenario Retriever`
- `AKG Writeback Candidates`
- scout-quality measurement surfaces

The design goal is to add a daily scenario layer on top of the existing deal-flow pipeline without changing live discovery, universe construction, collection, shortlist, or portfolio behavior.

## Decision Summary

The approved `v1` boundary is:

- automatic:
  - `Scout Compiler`
  - `Coverage Precheck`
- manual/on-demand:
  - full `Scenario Retriever`
- no automatic external retrieval
- no automatic scout reruns
- no live AKG mutation in `v1`
- every daily run should produce a daily scenario layer

This design is intentionally staged.

`v1` is about visibility, structure, and measurement, not actuation.

## Why This Boundary

The existing pipeline already does useful work:

- scouts surface candidates
- universe filter narrows the search space
- collectors enrich the narrowed set
- deeper analysis and portfolio logic consume that output

The missing piece is not raw sensing.

The missing piece is a compilation layer that turns daily scout evidence into:

- merged events
- scenario-ready summaries
- cross-scout narrative consolidation
- reusable question-time context

If this is inserted too early as a dependency, it will create pipeline risk before it has proven its value.

So `v1` must be:

- sidecar only
- artifact-first
- easy to inspect
- impossible to confuse with live scoring changes

## Non-Interference Principle

This is the most important operating constraint.

The new layer must not:

- alter universe membership
- alter collector inputs
- alter scoring
- alter shortlist construction
- alter deep-selection behavior
- alter portfolio planning
- mutate AKG directly
- trigger external APIs
- rerun scouts

The new layer may:

- read existing pipeline artifacts
- read current AKG state
- read current portfolio/watchlist/universe state
- write new sidecar artifacts
- emit preview-only AKG writeback candidates

## Runtime Placement

### Logical placement

Conceptually, the Scout Compiler belongs:

- after scouts
- before universe filter and collectors

because its job is to compile scout evidence into scenario-ready objects.

### Safe `v1` placement

Operationally, to preserve non-interference, it should run at the end of `discover()` after the existing daily artifacts are already built.

Current relevant seam:

- [pipeline.py](/Users/aeternusholdings/Documents/AeternusAgents-codex/tradingagents/dealflow/pipeline.py)

Specifically:

- after `scout_audit.json`
- after `discovery_delta.json`
- after `universe_filter.json`
- before `discover()` returns

This gives the compiler full visibility into the day’s scout outputs without letting it influence the existing path yet.

## New `v1` Components

### 1. Scout Compiler

Purpose:

- compile the day’s scout outputs into merged scenario objects
- create daily Event Cards
- preview future graph enrichments
- remain sidecar-only

### 2. Coverage Precheck

Purpose:

- cheaply score how complete each Event Card is
- help rank which events are retrieval-ready
- expose repeated evidence gaps

Rules:

- no LLM
- no external calls
- no scout reruns
- deterministic only

### 3. Scenario Retriever

Purpose:

- answer explicit scenario questions using internal state first
- explain when internal coverage is incomplete
- ask the user for missing inputs instead of automatically fetching

### 4. AKG Writeback Candidates

Purpose:

- preview what the compiler believes may later deserve graph enrichment
- remain non-executing in `v1`

### 5. Scout Quality Surfaces

Purpose:

- judge scouts and source bundles by conversion quality and realized edge
- extend current attribution into scenario-aware measurement

## Scout Compiler Inputs

The compiler should consume only data already generated by the daily run.

### Required inputs

- `as_of_date`
- `scout_audit.json`
- `discovery_delta.json`
- `universe_filter.json`

### Optional inputs

- manual X-feed merged payload
- FVG recall artifact
- FMA recall artifact
- macro cache
- read-only AKG
- read-only portfolio snapshot
- read-only current universe ledger

### Input principle

The compiler should not call scouts directly.

It should only compile the outputs scouts already produced.

## Artifact Set

`v1` writes four primary artifacts:

- `eval_results/deal_flow/<date>/event_cards.json`
- `eval_results/deal_flow/<date>/coverage_precheck.json`
- `eval_results/deal_flow/<date>/scout_compiler_debug.json`
- `eval_results/deal_flow/<date>/akg_writeback_candidates.json`

These artifacts are sidecar-only and should be easy to diff and inspect.

## Event Card Contract

One Event Card represents one merged daily event or scenario narrative.

### Required fields

- `event_card_id`
- `date`
- `title`
- `event_type`
- `summary`
- `source_bundle`
- `source_records`
- `direct_entities`
- `second_order_entities`
- `channels`
- `expected_direction`
- `confidence`
- `urgency`
- `time_horizon`
- `portfolio_relevance`
- `matched_holdings`
- `matched_universe_symbols`
- `coverage_dimensions`
- `missing_dimensions`
- `followup_questions`

### Field definitions

#### `event_card_id`

Stable deterministic identifier for the card on that day.

Example:

- `evt_2026_03_15_iran_oil_cluster`

#### `event_type`

High-level canonical category.

Initial allowed values:

- `geopolitical_supply_shock`
- `policy_regulatory_shock`
- `earnings_options_setup`
- `technical_ignition`
- `insider_accumulation`
- `theme_rotation`
- `supply_chain_signal`
- `leading_indicator_signal`
- `cross_scout_narrative`

#### `source_bundle`

Flat list of contributing source families.

Examples:

- `["x_feed", "commodity_shock_scout", "macro"]`
- `["technical_ignition", "fvg_recall"]`

#### `source_records`

Trace-level provenance records.

Each record should include:

- `source_family`
- `raw_symbol`
- `catalyst_or_reason`
- `artifact_hint`

#### `direct_entities`

Entities directly implicated by the event.

May include:

- tickers
- ETFs
- commodities
- countries
- officials
- sectors

Each item should be normalized into:

- `entity_type`
- `entity_id`
- `label`

#### `second_order_entities`

Entities not explicitly named in the raw scout output but inferred through rule-based daily compilation.

These must remain visibly lower-confidence than direct entities.

#### `channels`

Causal lanes by which the event is expected to matter.

Initial allowed values:

- `oil`
- `defense`
- `risk_off`
- `volatility`
- `rates`
- `supply_chain`
- `ai_capex`
- `consumer_demand`
- `credit`
- `technical_momentum`
- `insider_signal`
- `policy_exposure`

#### `expected_direction`

Map from entity id to one of:

- `up`
- `down`
- `mixed`
- `unknown`

#### `confidence`

Float `0.0-1.0`.

In `v1`, this should be deterministic and derived from:

- source diversity
- cross-scout confirmation
- direct vs inferred entity ratio

#### `urgency`

One of:

- `immediate`
- `near_term`
- `developing`

#### `time_horizon`

One of:

- `intraday`
- `1d_to_5d`
- `5d_to_20d`
- `20d_plus`

#### `portfolio_relevance`

One of:

- `high`
- `medium`
- `low`
- `none`

#### `coverage_dimensions`

Evidence dimensions already present for this event.

Initial dimension set:

- `social`
- `macro`
- `technical`
- `commodity`
- `filing`
- `portfolio`
- `supply_chain`
- `insider`

#### `missing_dimensions`

Dimensions that appear likely to matter but are not currently covered well enough.

#### `followup_questions`

Questions that a later Scenario Retriever or operator may want to answer.

Examples:

- `How exposed are current holdings to this event?`
- `Which defense names benefit most after first-order winners?`
- `Do we need a hedge now or just a watchlist adjustment?`

## Coverage Precheck Contract

The Coverage Precheck is automatic and cheap.

It exists to tell us:

- which Event Cards are already well-formed
- which are thin
- which repeatedly lack the same evidence dimensions

### Inputs

- `event_cards.json`
- read-only AKG
- read-only universe
- read-only portfolio context
- local artifact presence checks

### Outputs

`coverage_precheck.json` should contain:

- `date`
- `rows`
- `summary`

Each row should include:

- `event_card_id`
- `coverage_status`
- `coverage_score`
- `entity_resolution_score`
- `source_diversity_score`
- `channel_confirmation_score`
- `portfolio_relevance_score`
- `freshness_score`
- `missing_dimensions`
- `ready_for_retrieval`
- `coverage_notes`

### Coverage status definitions

#### `COMPLETE`

- main entities resolved
- at least one plausible direct impact path exists
- no critical missing dimension remains
- internal evidence is sufficient for a responsible first-pass answer

#### `PARTIAL`

- some entities or paths are resolved
- useful provisional answer is possible
- one or more critical dimensions are missing, stale, or weak

#### `MISSING`

- core event or core entities remain unresolved
- or the event lacks enough internal evidence to answer responsibly

### `v1` scoring principle

No LLM calls.

No semantic inference beyond deterministic rules and artifact presence.

This is an internal coverage precheck, not a world model.

## AKG Writeback Candidates Contract

This artifact is preview-only in `v1`.

It exists so we can inspect what the compiler thinks may later deserve graph writeback without mutating AKG.

### Required fields

- `candidate_id`
- `candidate_type`
- `source_entity`
- `target_entity`
- `relationship`
- `payload`
- `confidence`
- `evidence_event_cards`
- `durability`
- `writeback_recommendation`

### Allowed `candidate_type`

- `edge`
- `event_summary`
- `entity_alias`
- `relationship_claim`

### Allowed `writeback_recommendation`

- `safe_later`
- `needs_review`
- `temporary_only`

### Example

```json

  "candidate_type": "edge",
  "source_entity": "XLE",
  "target_entity": "UAL",

    "direction": "negative"

  "durability": "temporary",
  "writeback_recommendation": "needs_review"
}
```

## Scenario Retriever Contract

The Scenario Retriever is manual/on-demand only in `v1`.

### Why it is not automatic

Automatic full retrieval would:

- spend compute on questions nobody asked
- create noisy low-value output
- tempt future auto scout reruns
- blur the non-interference rule

So `v1` should only run it:

- on explicit user question
- or on explicit operator expansion of one Event Card

### Inputs

- `question`
- optional `event_card_id`
- optional `ticker_scope`
- optional `portfolio_scope`

### Search order

1. `event_cards.json`
2. `coverage_precheck.json`
3. AKG
4. current filtered universe
5. current holdings / shortlist / queue
6. cached macro
7. cached SEC / filing artifacts
8. cached X-feed artifacts

### Outputs

- `question`
- `coverage_status`
- `matched_event_cards`
- `matched_entities`
- `direct_impacts`
- `second_order_candidates`
- `portfolio_impacts`
- `hedge_candidates`
- `missing_inputs`
- `recommended_manual_gap_fill`
- `wait_for_user`

### Required behavior on gaps

If coverage is incomplete, the retriever must:

- say what it is missing
- explain which missing evidence blocks a responsible answer
- wait for user input

It must not:

- automatically call APIs
- automatically rerun scouts
- automatically trigger Grok/manual prompt flows

This is a strict operating rule.

## Scout Quality Measurement

The user explicitly requested that scout quality be measured as well.

The system already has parts of this:

- `scout_audit.json`
- `discovery_delta.json`
- `source_attribution.json`
- hindsight / performance review
- `why_missed`

The new scenario layer should extend that rather than replace it.

### Proposed artifacts

Not required in the first code slice, but part of the same design:

- `scout_quality_daily.json`
- `scout_quality_rolling.json`

### Metrics to compute

- detection count by scout family
- universe inclusion rate
- shortlist conversion rate
- deep-selection conversion rate
- realized `5d/20d` edge by scout family
- Event Card contribution by source bundle
- coverage-complete rate by source bundle
- cross-scout confirmation edge
- `why_missed` overlap rate

### Why this matters

Once Event Cards exist, scouts can be judged not just by “did they fire?” but by:

- did they help create useful daily scenarios?
- did those scenarios become retrieval-ready?
- did those scenarios matter for selection or performance?

## Rules-Based vs LLM-Based Boundary

`v1` should stay mostly rules-based.

### Deterministic in `v1`

- entity normalization
- source bundling
- event-type assignment from known rule sets
- coverage precheck
- AKG writeback candidate generation

### Deferred from `v1`

- LLM-generated narrative summaries
- LLM-generated investor-doc text
- LLM-based retrieval expansion
- LLM-inferred graph writeback

This keeps the first slice auditable and cheap.

## Risks

### Risk 1: premature semantic ambition

If `v1` tries to infer too much, the Event Cards will become noisy and untrustworthy.

Mitigation:

- keep `v1` deterministic and conservative

### Risk 2: hidden pipeline coupling

If sidecar outputs start getting consumed informally, the system will drift into silent dependency.

Mitigation:

- explicitly keep artifacts read-only and sidecar-only in `v1`

### Risk 3: event explosion

Daily runs may produce too many weak cards.

Mitigation:

- require cross-source or strong single-source thresholds
- collapse duplicates aggressively

### Risk 4: confusing hypotheses with facts

Second-order implications can look more certain than they are.

Mitigation:

- separate direct entities from second-order entities
- keep preview writeback candidates separate from AKG

## Success Criteria

`v1` is successful if:

- every `discover()` run writes the four new sidecar artifacts
- live pipeline behavior is unchanged
- Event Cards are understandable and audit-friendly
- coverage precheck correctly distinguishes thin vs rich daily scenarios
- Scenario Retriever can answer internal questions without external calls
- when it cannot answer, it clearly lists missing evidence and waits for the user
